# Benchmark methodology

## Workloads and correctness

All engines read the same immutable Parquet file. Average fare ignores nulls; distance counts strictly greater than 5 (not >=5); daily groups by calendar pickup date and includes null dates. Full date-to-count mappings are validated, not just totals. The legacy `result` for daily remains the sum; `value` holds the mapping. An independent Arrow reference validates every warmup and measured repetition. Counts/maps must match; average uses relative and absolute tolerance 1e-9. Data is not cleaned: negative fares and unusual dates are preserved.

## Timing boundaries

A fresh Python subprocess runs each sample. End-to-end starts immediately before engine import and ends after the materialized query result; it includes import, setup, file read, planning and execution, but excludes Python process launch, measurement imports, reference validation and serialization. Pandas eagerly reads the three shared columns; lazy engines can project/prune and use Parquet statistics. These optimization differences are intentional and may make a count metadata dominated.

In-memory excludes engine import and eager loading. Pandas loads a dataframe, Polars loads then creates a lazy frame, DuckDB creates a native table, DataFusion registers eager Arrow record batches. Query time includes planning, grouping and result materialization; there is no untimed query warmup inside a measured process. Setup time and query time are recorded separately. Memory layouts differ, so this compares engine workflows, not identical physical representations.

One separate-process warmup per engine is discarded by default. Measured engine order is shuffled each round with seed 42. Report the median with min/max and raw samples, not a best run. OS filesystem cache is never flushed. Fingerprinting and reference reads warm the cache before samples; these are explicitly warm-cache experiments, not cold-disk benchmarks. Run on an idle machine, plugged in, with consistent power settings. The API serializes benchmark and explorer work within one server process; use one server worker and do not run parallel CLI jobs.

## Memory and parallelism

Whole-process peak RSS includes imports and setup even in in-memory mode. Unix uses the process high-water mark (bytes on macOS, KiB on Linux), combined with a 5 ms RSS sampler. Windows uses the sampler and may miss short spikes. MB means MiB (2^20 bytes). Medians of per-process peaks are displayed, not incremental allocations or system-wide memory.

DuckDB and DataFusion use the requested thread/partition setting, Polars uses POLARS_MAX_THREADS and Arrow ARROW_NUM_THREADS is set before engine import. Pandas algorithms and native libraries may use different parallelism; this is not guaranteed equal CPU utilization. Record engine versions and hardware with results. For stronger reproducibility, commit dependency lockfiles and preserve dataset hashes; row-order determinism only applies to the same source artifact. Do not compare different data hashes or timing modes as one series.

## Data provenance

The downloader uses Yellow Taxi January–August 2023 from the NYC TLC CDN. It uses a single-threaded, ordered file list to create exactly 10M rows; preparation derives 100K and 1M prefixes. These are nested performance fixtures, not randomized samples for inference. Existing local 10M files may have been generated by older code; their SHA-256 identifies the actual artifact. API metadata asserts exact row count before benchmarking. Dataset downloads and generation happen outside timed runs.

Limits: no cold-cache controls, CPU energy measurements or confidence intervals; engine order cannot eliminate thermal effects. DataFusion's Python/Arrow bridge is included where it occurs inside the selected timing boundary. Historical v0.1 observations are documented separately and not inserted as newly measured history.
